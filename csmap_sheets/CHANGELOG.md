# v0.10.0 — 傾斜計算方式の選択（既定をHorn法に変更）、森林TIFFの欠測値・CRS自動推定の修正、文言整理

**重要（既定動作の変更）**：傾斜の計算方式の既定を、中央差分法からHorn法に変更した。v0.9.4以前と同じ設定でも、傾斜に由来する色（傾斜A・B、独自方式の傾斜の暗さ）が変わる。以前の出力を再現する場合は、パラメータ「傾斜計算のアルゴリズム」で「中央差分法（従来互換）」を選ぶ。

傾斜計算方式の選択（新機能、ユーザー決定、2026-10-02）:

- `engine/pipeline.py`：設定キー`slope_algorithm`（`horn`／`central_difference`、既定`horn`）と、勾配を計算する`slope_gradients()`を追加。`relief()`はこれを使う。不正な値は`validate_config()`と`relief()`でエラーにする。
  - `horn`：Horn (1981) の3×3加重差分。`dz/dx=((z3+2z6+z9)-(z1+2z4+z7))/(8d)`、`dz/dy=((z7+2z8+z9)-(z1+2z2+z3))/(8d)`。
  - `central_difference`：2点の中央差分。v0.9.4までの計算をそのまま再現する。
  - どちらも平滑化前のDEMを使う。欠測の扱い（計算に使う範囲に欠測を含む画素を透過）は変更なし。Horn法の3×3近傍に欠測があれば、その画素は透過される。
- 選んだ方式は、独自方式（v0.4互換）とFMEマニュアル方式のどちらにも使う。組込み設定プロファイルでも、利用者の選択（既定Horn法）に従う。キーを持たない外部JSONプロファイル（v0.9.4以前の保存）を読み込んだ場合は、画面の選択（既定Horn法）が使われ、その旨と中央差分法で再現できることをログに警告として表示する。
- `run.json`の`settings.slope_algorithm`と`rendering.terrain_calculation`（`slope_algorithm`と方式の説明）に記録する。GeoTIFFの`SETTINGS`メタデータにも同じ設定JSONを通じて残る。QGISのログに「傾斜計算方式: Horn法／中央差分法」を表示する。
- `algorithm.py`：パラメータ「傾斜計算のアルゴリズム」（`SLOPE_ALGORITHM`）を追加。既定動作の変更に気づけるよう、詳細パラメータではなく通常の項目として表示する。「傾斜の暗さが飽和する角度」（`SLOPE_MAX`）は色調の設定であり、計算方式とは別であることを表示名に明記。
- PSS版（FMEワークスペース）の`RasterSlopeCalculator`はHorn法を選んでいるが、欠測の補間・外縁の扱い・平滑化の条件が異なるため、Horn法にしても画素単位の完全一致は目標にしない。

その他（未リリースだった変更）:

- 文書・コメント・画面表示の文言を整理（機能変更なし）。
- 森林航空レーザ成果のTIFFで、NoData設定と異なる欠測値（`-9999`、`-1111`）が標高として扱われていた不具合を修正。該当画素をNoDataに置き換えたコピーを作業フォルダーに作り、件数をログと`input_report.json`の`extra_nodata_cells`に記録する。該当画素が無い入力ではコピーを作らない。
- `INPUT_GUIDE_ja.md`に、上記の扱いと、0.1m刻みの標高データで曲率レンジを狭くした場合の注意を追記。
- 出力座標系（CRS）を未指定にして「入力フォルダー」を指定すると、フォルダー自体を開こうとして自動推定が必ず失敗していた不具合を修正。フォルダー内の先頭のラスターファイル（パスの小文字順。「サブフォルダーも検索する」の設定に従う）で推定する。該当ファイルが無い場合は、これまでどおり明確なエラーで停止する。
- GitHub ActionsでGDALなしのユニットテストを自動実行するようにした。

検証：GDAL/PDAL/QGISなしの環境でユニットテスト一式を実行（件数はVALIDATION.txt参照）。**未確認**：QGIS 3.44・Windows実機での動作、FME出力との画素比較。

# v0.9.4 — XYZ最大ズーム標準値見直し・候補タイル数超過の早期検出・CRS自動推定エラーメッセージ改善

v0.9.3の実機テスト（2026-09-30、京都DEMの検証用データ）で判明した2点への対応と、同テスト中に
ユーザーから提案されたCRS自動推定エラーメッセージの改善。

1. **XYZタイル最大ズームの標準値変更**：`XYZ_MAX`（最大ズームレベル）の既定値を18から16へ
   変更（`algorithm.py`、`engine/xyz_tiles.py`の`DEFAULTS`）。運用では、標準の
   `xyz_max_tiles`上限（10万枚）を超えやすいことが判明したため。
2. **XYZ候補タイル数超過の検出を前倒し（フェイルファスト、重要）**：従来、候補タイル数が
   上限を超える場合の検出は`write_xyz()`内部、すなわちCS立体図の計算(`render_sheets()`、
   本プラグイン最重量の処理、実測で1066図郭・約1時間32分)と結合GeoTIFF書き出しが完了した
   **後**に行われていた。実機テストで、2時間15分の計算後に候補タイル数超過
   （551,912枚 > 上限100,000枚）で失敗する事象が発生（ユーザー報告、2026-09-30）。
   投影済みDEM（`projected_dem.vrt`）の範囲から同じ計算式で候補タイル数を見積もる
   `precheck_xyz_tile_count()`を新設し、`render_sheets()`を呼ぶ前に検証するよう変更
   （`engine/xyz_tiles.py`、`engine/pipeline.py`の`run()`）。超過が判明していれば、
   重い計算を一切走らせず即座に停止する。見積りに使う範囲はCS立体図そのもの（図郭境界に
   合わせてわずかに拡張され得る）とは厳密には一致しないため、最終的な安全性は従来どおり
   `write_xyz()`内の本チェックで担保する（二重チェック、片方が甘くてももう片方が守る設計）。
3. **CRS自動推定エラーメッセージの改善**：v0.9.3で追加した出力CRS自動推定が失敗した場合の
   理由を、「CRS情報が全く無い（TIFF＋TFWワールドファイルなど）」場合と「CRSはあるが
   平面直角座標系第I～XIX系のいずれとも一致しない」場合とで区別できるよう、
   `infer_target_crs_from_raster()`の戻り値を`wkt`単体から`(wkt, reason)`のタプルへ変更
   （ユーザー提案、2026-09-30。`engine/pipeline.py`）。

回帰テスト計4件追加（`tests/test_xyz.py`3件、うち1件はGDAL実行環境依存でスキップ）。
全99件（実機依存10件スキップ）でリグレッションなしを確認。

**未検証**：本開発環境にはosgeo(GDAL/OSR)が入っておらず、`precheck_xyz_tile_count()`の
GDAL統合テストはスキップされたまま（数式部分の`estimate_candidate_tiles()`のみ純粋な
Pythonロジックとして検証済み）。1〜3すべてWindows/QGIS実機での動作確認は未実施。

# v0.9.3 — 個別ファイル選択のQGIS長時間ハング対策・入力操作性改善・結合GeoTIFF・出力CRS自動推定

ユーザー報告（2026-09-30、v0.9.2実機運用中）に基づく5点の修正・機能追加。詳細な経緯・調査結果・

# v0.9.2 — v0.9.1の.txt対応が招いたQGIS「応答なし」ハングの修正（重大・回帰）

- **これはv0.9.1で新たに混入した回帰バグであり、QGIS本体側の不具合ではない。** 原因は本プラグインの
  実装ミス。v0.9.1でLEM対応メタデータ判定の対象拡張子に`.txt`を追加した際、判定対象になり得る
  `.txt`ファイルの実際のサイズを考慮していなかった。
- 背景：ユーザー報告（2026-09-30、実機`hyogo_lem_1m`データセット）。`.lem`本体とペアの
  `lem形式`フォルダーとは別に、同じ命名規則の**単体**`.txt`グリッドファイルが大量に存在する
  `txt形式`フォルダーが検証用データに含まれることが判明。これらは`.lem`companionを持たない、
  それ自体が標高値を含む独立したテキストグリッドで、サイズは16KB〜約97MBに達する
  （例：`06je983_1g.txt`が約20MB、714ファイル）。
- v0.9.1の`is_lem_metadata()`はLEMメタデータ判定のためにファイル**全体**を`Path.read_bytes()`で
  読み込んでいた。`txt形式`フォルダーのような大容量`.txt`が多数（実例714件）存在する場合、
  `classify_sources()`がそれぞれに対してこの全文読み込みを行い、大量のI/O・メモリ確保が
  積み重なってQGISが長時間「応答なし」になる不具合を引き起こしていた（CPU使用率はほぼ0%で
  メモリは数百MB程度に留まっていたことから、CPUバウンドではなくI/O/メモリ確保待ちの停止と
  推定。仮定：この推定はプロセス全体のプロファイリングではなく、タスクマネージャーの概況
  観測に基づく未確認事項）。
- 修正：`is_lem_metadata()`をファイル先頭の固定バイト数（`LEM_METADATA_PROBE_BYTES = 262144`、
  256KiB）のみを読む「プローブ」方式に変更した（新設`_decode_head()`）。実測した本物の
  LEM対応メタデータCSVは最大でも約35KBだったため、256KiBは約7倍の安全マージンを持つ
  （仮定：将来、35KBを大きく超える本物のメタデータファイルが現れた場合、このプローブ範囲を
  超えると誤ってgrid扱いされる可能性がある未確認の残存リスク。現時点ではこのリスクより
  巨大ファイルでのハングを防ぐことを優先した）。ファイル全体を読む`read_lem_metadata()`は
  `is_lem_metadata()`で候補と確認された後にのみ呼び出す用途に限定し、動作は変更していない。
- 回帰テスト追加（`tests/test_inputs.py`）：(1) プローブ上限を超える巨大`.txt`（スパースファイルで
  実容量を消費せず模擬）に対して`open().read()`に渡されるサイズが常にプローブ上限以下であることを
  `builtins.open`のモックで検証、(2) 実測に近い約35KBの本物メタデータがプローブ上限内で
  正しく認識されることを確認、(3) 大容量の単体`.txt`グリッドが引き続き`grid`として分類され、
  メタデータ判定の全文読み込みでハングしないことを確認。全88件（うち実機依存9件スキップ）で
  リグレッションなしを確認済み（開発環境上のユニットテストのみ。QGIS/Windows実機での
  再現手順を用いた確認は未実施、ユーザーによる実機再検証待ち）。
- **未検証**：この修正が、当初報告された`AlgorithmDialog.asMap()`での`Exception: unknown`
  （パラメータ収集段階の例外）と同一原因かどうかは未確認。本ハングとは別に、そちらの例外が
  独立した問題として残っている可能性がある（該当箇所の「スタックトレース」表示内容は
  未取得）。ユーザーには、修正版で`hyogo_lem_1m`の`txt形式`・`lem形式`双方を再テストし、
  例外が再発するかどうかの確認を依頼中。

# v0.9.1 — LEM対応メタデータの.txt拡張子対応

- 背景：ユーザー報告（2026-09-30）。森林航空レーザ成果（LEM）入力の検証用データで、`.lem`ファイルに
  対応するメタデータファイルが、規則上は`.csv`拡張子のはずだが実態として`.txt`拡張子で提供される
  場合が多いことが判明（例：`glid_1m/csv形式/06je983_1g.txt`）。従来の`expand_sources()`/
  `classify_sources()`は対応ファイルの探索を`.csv`拡張子に固定していたため、`.txt`のみの
  データセットでは対応メタデータが見つからず`ValueError('LEM requires its companion metadata
  CSV with the same stem: ...')`で停止していた（未確認だが、QGIS実機で報告された
  `AlgorithmDialog.asMap()`での`Exception: unknown`とは別事象の可能性が高い。あちらは
  パラメータ収集段階でこのコードより前に発生しており、根本原因は別途トレースバック確認中）。
- 対応：LEMメタデータの判定は元々拡張子ではなく中身のCSV構造（`is_lem_metadata()`が
  `東西方向の点数`等の必須フィールドの有無をチェック）で行っているため、探索対象の拡張子に
  `.txt`を追加するだけで拡張子非依存の判定をそのまま活用できる。同一ファイル名(stem)に
  `.csv`と`.txt`が両方存在する場合は、従来の`.csv`前提の挙動を変えないよう`.csv`を優先する
  （仮定：現場データはどちらか一方のみのはずで、優先順位が実害になるケースは想定していない）。
- `.txt`は単体のXYZ/CSVグリッド入力としても使われる拡張子のため、LEM companion判定は
  「同名`.lem`が存在し、かつ内容がLEMメタデータ構造に一致する場合のみ」に限定し、通常の
  XYZグリッド用`.txt`ファイルの分類（`grid`扱い）には影響しない。
- 対応する`.lem`/`.csv`/`.txt`のいずれも見つからない場合は、従来どおり明確なエラーで
  即座に停止する（黙ったフォールバックは行わない、PNG/WebPと同じ「フェイルファスト」方針）。
- 回帰テスト追加（`tests/test_inputs.py`）：`.txt`companionのみでLEM分類が成功すること、
  `.csv`/`.txt`が同一stemで両方存在する場合に`.csv`が優先されること、単体`.txt`グリッドの
  分類が従来どおり`grid`のままであることを検証。GDAL/QGIS実機は不要でこの開発環境でも
  実行可能。全85件（うち実機依存9件スキップ）でリグレッションなしを確認済み。
- **未検証**：本修正がWindows/QGIS実機の検証用データ（`glid_1m/csv形式/`）で実際にLEM入力を
  完走させられるかは未確認。前回報告された`AlgorithmDialog.asMap()`の例外との関連含め、
  実機での再検証が必要。

# v0.9.0 — WebP非可逆(lossy)出力の追加

- 背景：ユーザーから「WebPだが非可逆を求められた」との要望（2026-09-28）。v0.8.0では
  WebPは可逆(lossless)のみ実装していたが、配信先クライアントの要件により非可逆(lossy)が
  必要になったため、以前議論・確認済みの仕様（GDAL WEBPドライバのQUALITY・LOSSLESSオプション、
  gdal.org WEBPドライバページで確認）どおりに選択式で追加した。
- 「XYZ画像形式」でWebPを選んだ場合、新設の「WebPを可逆(lossless)にする」（既定True＝従来どおり
  可逆）を無効にすると非可逆になり、「WebP非可逆時のQUALITY」（1-100、既定75、GDAL WEBPドライバの
  既定値と同じ）で圧縮率を指定できる。両パラメータともAdvanced（詳細パラメータ）扱い。
- 実装は`_tile_encoder()`の作成オプションを条件分岐：可逆時は`LOSSLESS=TRUE`（従来どおり）、
  非可逆時は`LOSSLESS=FALSE`＋`QUALITY=<値>`を明示的に指定（GDALの暗黙のデフォルトに頼らない）。
- WEBPドライバが利用できない環境では、可逆・非可逆いずれの設定でも**従来どおりPNGへ黙って
  切替えず**、明確なエラーで停止する（PNG/WebP・LEMいずれの経路とも同じ「フェイルファスト」方針）。

# v0.8.1 — 森林航空レーザ（LEM）入力の応答なし不具合修正

- 背景：ユーザー報告（2026-09-28「Lemが流れない」）。森林航空レーザ成果（LEM・CSV格子・TIFF・
  GeoTIFF・ZIP）を入力形式として、794件の`.lem`ファイル（同名の`.csv`メタデータを1件も伴わない
  データセット）を選択して実行すると、QGISのウィンドウタイトルに「(応答なし)」が表示されたまま
  長時間戻らず、ログタブへの切替えもできなくなる（＝UIメインスレッドがブロックされている状態）。
- 原因：`engine/forest_dem.py`の`expand_sources()`で、`.lem`ファイルに対応する同名`.csv`が
  直接存在しない場合、`path.parent.glob('*')`でフォルダ内の全ファイルを毎回再走査してから
  ステム名一致を探していた。対応CSVを持たないLEMファイルがN件あると、この再走査がN回発生し、
  1回あたりの走査コストもフォルダ内ファイル数に比例するため、全体としてO(N²)のファイルシステム
  走査になる（本件N=794では概算約63万回のファイルエントリ比較に相当）。この処理は
  `algorithm.py`の`prepareAlgorithm()`（`validate_config()`→`discover()`経由）から呼ばれており、
  QGIS Processingではこの`prepareAlgorithm()`がUI/メインスレッド上で実行されるため、走査が
  終わるまでQGIS全体の描画・入力処理が止まっていた。
- 修正：`expand_sources()`にディレクトリ単位の`.csv`一覧キャッシュ（`csv_index_cache`）を追加し、
  同一フォルダに対する全件列挙を1回だけ行うように変更（O(N²)→O(N)＋ディレクトリ数分の列挙）。
  拡張子の大文字小文字を区別しない挙動（修正前の`p.suffix.lower()=='.csv'`判定）は維持している。
- **これは性能の不具合修正であり、データ要件そのものは変更していない**：`.lem`ファイルには
  依然として同名の`.csv`メタデータが必須であり、見つからない場合は`classify_sources()`が
  従来どおり`ValueError('LEM requires its companion metadata CSV with the same stem: ...')`で
  即座に停止する（PNG/WebPの方針と同様、要件を満たさない場合に黙ってスキップ・代替しない）。
  本件の794件のデータセットに`.csv`が実在しない場合、この修正だけでは処理は成功せず、
  数十秒程度で明確なエラーメッセージが出るようになる、という違いになる。`.csv`メタデータの
  所在確認・入手はユーザー側の対応が必要。
- 回帰テスト追加（`tests/test_inputs.py`）：対応CSVを持たないLEMファイル50件に対して、
  同一ディレクトリの列挙が1回だけであることをカウント検証するテスト、および大文字小文字が
  異なる`.csv`（例：`A.CSV`）でもキャッシュ経由で対応付けできることを検証するテスト。
  GDAL/QGIS実機は不要でこの開発環境でも実行可能。全80件（うち実機依存8件スキップ）で
  リグレッションなしを確認済み。
